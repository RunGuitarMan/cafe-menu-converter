# Конвертер меню кафе

Автономное GUI-приложение на .NET 10 / Avalonia для Windows x64 и macOS Apple Silicon / Intel. Превращает текстовые PDF установленного шаблона в XLSX. Интернет, Excel, установленный .NET, Python и Node.js для запуска готовой сборки не нужны. Шрифты, библиотеки и стандартные настройки включены в приложение.

Готовые приложения: [GitHub Releases](https://github.com/RunGuitarMan/cafe-menu-converter/releases/latest). Исходники хранятся в репозитории, большие бинарные файлы — в Releases.

## Запуск

- Windows x64: скачайте **`CafeMenuConverter-win-x64.exe`**, скопируйте в удобную папку и запустите. Это один самостоятельный EXE; соседние DLL и конфиг не нужны. Установщика нет. Неподписанный EXE может вызвать предупреждение SmartScreen.
- macOS 14 и новее, Apple Silicon (M1 и новее): распакуйте **`CafeMenuConverter-osx-arm64.zip`**, перенесите **`CafeMenuConverter.app`** в удобную папку и откройте.
- macOS 14 и новее, Intel: аналогично используйте **`CafeMenuConverter-osx-x64.zip`**. Для обеих архитектур есть нативная сборка; Rosetta не требуется.

Текущие macOS-сборки имеют ad-hoc подпись, без нотарификации Apple: Developer ID пока не предоставлен. Для доверенной скачанной сборки разрешите первый запуск в системных настройках безопасности, если macOS его заблокирует. Это ограничение подписи издателя, а не требование установить зависимости. Конвейер Developer ID / нотарификации подготовлен ниже.

Windows-сборка рассчитана на x64-версии Windows, поддерживаемые [.NET 10](https://learn.microsoft.com/dotnet/core/install/windows), включая Windows 11. Windows 7/8.1 и 32-битная Windows не поддерживаются. Права администратора для работы приложения не нужны.

1. Выберите PDF кнопкой или перетащите один файл на область выбора.
2. Выберите офис: Space, Водный или ОКО. Офис намеренно не выбран по умолчанию.
3. При необходимости измените путь XLSX; по умолчанию результат сохраняется рядом с PDF.
4. Нажмите **Конвертировать**. Вкладки показывают сводку, блюда и диагностику.

Перезапись существующего файла требует подтверждения. При ошибках PDF файл не создаётся. При неудачном сохранении старый XLSX остаётся целым. Если файл открыт в Excel, закройте его перед повторной попыткой. Отмена доступна во время обработки. Закрытие окна во время обработки сначала отменяет операцию; после отмены окно можно закрыть.

## Правила данных

Категория — **заголовок раздела PDF дословно**, с сохранением регистра. Автоматического распределения на «Каши», «Горячие блюда» и другие категории нет. Например, `Горячее блюдо или каша` остаётся одним разделом. Названия, состав, опечатки и ошибочная строка с `125ГР Т БАНК` переносятся как в PDF, без исключений для отдельных блюд. Это соответствует уточнению пользователя от 13.10.2026.

Стандартные разрешённые заголовки из [config/categories.json](config/categories.json) встроены в приложение. **Конфиг необязателен: если файла нет, используются встроенные значения; если есть — он целиком заменяет их.** Сравнение не зависит от регистра, но в XLSX сохраняется регистр исходника.

Чтобы изменить список, скопируйте пример `categories.json`, отредактируйте и разместите его:

- Windows: рядом с запускаемым EXE, независимо от его имени и текущей рабочей папки.
- macOS: `~/Library/Application Support/CafeMenuConverter/categories.json`. Папку можно открыть через Finder → «Переход» → «Переход к папке» и создать при необходимости. Содержимое `.app` редактировать не нужно; подпись сохраняется.

Изменения подхватываются при следующей конвертации. Пустой, повреждённый, недоступный файл или повторяющиеся категории дают ошибку; приложение не подменяет ошибочный конфиг дефолтами молча. Удаление файла возвращает встроенные настройки. Конфиг из старых сборок, лежавший внутри `.app`, нужно перенести в указанный пользовательский каталог.

| Поле | Правило |
| --- | --- |
| office | Space: `7f98361b-7b8d-40f0-bdec-0ef6d811afbf`; Водный: `22ee2228-41b9-4db0-8fb4-1a0217cf41af`; ОКО: `a5d27432-a5af-41c6-bc91-9b7ce3ce09b2` |
| date | Дата из шапки, `yyyy-MM-dd`; двухзначный год относится к 2000–2099 |
| type | `08:30–10:30` → `Завтрак`; `12:00–17:00` → `Обед`; другое время — ошибка |
| category / name | Текст PDF; строки соединяются пробелом, после конечного дефиса или `/` в названии пробел не добавляется |
| product_composition | JSON-массив; запятые внутри скобок и между цифрами не разделяют ингредиенты; переносы слов в составе склеиваются без дефиса; пустой состав — пустая ячейка |
| weight | `150/20 гр.` → `["150","20"]`; без единицы массы предполагаются граммы, как согласовано |
| unit / quantity | `1 шт (65гр).` → `["65"]`, `гр.`, `1`; `3 шт.` → пустые масса и единица, количество `3` |
| price | Число перед `₽` |
| calories / protein / fats / carbohydrates | Все четыре нуля → пустые ячейки и предупреждение; отдельные нулевые значения сохраняются |

Нет отдельного выхода в PDF → пустые weight/unit/quantity. Значения из названия не извлекаются. Неизвестный формат выхода — ошибка.

Выход: один лист `Data`, 14 колонок в порядке референса, включая пустые ячейки. Все ячейки — shared strings, в том числе даты и числа. Заголовок жирный, серый, по центру; добавлены фильтр и закрепление первой строки. Кавычки и кириллица сохраняются; состав и вес — валидный JSON. CSV не генерируется.

## Поддерживаемый PDF

Поддерживаются два проверенных макета: две колонки и таблица завтрака. Разбор учитывает координаты, размеры шрифта и белый текст заголовков. Шрифты Type 3 в этих PDF не сообщают достоверное имя гарнитуры: PdfPig возвращает `Type3`, поэтому классификация по имени Bold не применяется.

Страницы группируются по дате, их исходный порядок внутри дня сохраняется. Число страниц на день не фиксировано. Блюдо может продолжаться в следующей колонке или на следующей странице того же дня. Число блюд сверяется с числом цен; проверяются цена, КБЖУ, раздел, формат выхода и нераспознанные слова. Незнакомый макет должен давать диагностику, а не частичный XLSX.

Это парсер конкретного шаблона, а не универсальный распознаватель любых меню. Сканы без текстового слоя, зашифрованные PDF, другое время в шапке и изменённые размеры/структура вёрстки требуют нового референса и доработки. OCR и внешние AI-сервисы не используются. Качество исходных данных (ошибочный состав, неверные КБЖУ) автоматически не исправляется.

## Разработка и сборка

На машине разработчика требуется .NET SDK 10; выбор SDK описан в `global.json`. Python 3 нужен для проверки упаковки и релизов. Эти инструменты не нужны пользователю приложения.

```sh
dotnet test CafeMenuConverter.sln
dotnet run --project src/CafeMenuConverter.App
bash build/publish.sh
```

Скрипт на macOS запускает Release-тесты и собирает `win-x64`, `osx-arm64`, `osx-x64`. Можно передать один или несколько RID: `bash build/publish.sh osx-arm64`. Каталоги публикации и staging создаются заново, чтобы старые файлы не попадали в релиз.

Общие настройки автономной публикации закреплены в `build/Standalone.props`: `SelfContained=true`, `PublishSingleFile=true`, runtime .NET **10.0.12**, trimming отключён. В Windows нативные библиотеки встроены в EXE и автоматически распаковываются во временный пользовательский кеш .NET при запуске; это не установка и не требует административных прав. В macOS нативные библиотеки лежат внутри подписанной `.app`. Все её компоненты подписываются перед подписью самого пакета.

`build/verify-package.py` читает манифест внутри готового исполняемого файла, проверяет встроенный runtime и библиотеки, отсутствие обязательного конфига и ровно один EXE в Windows-публикации. Результаты находятся в `artifacts/releases`: EXE, два ZIP с `.app` и необязательный `Third-party-notices.zip`. Лицензии также встроены в EXE и включены в `.app`.

Для сборки Windows на Windows:

```powershell
powershell -ExecutionPolicy Bypass -File build/publish.ps1
```

Для подписанного и нотарифицированного macOS-релиза разработчик заранее устанавливает сертификат Developer ID Application и сохраняет учётные данные `notarytool` в Keychain. Перед сборкой задаются `MACOS_SIGN_IDENTITY` (имя сертификата) и `MACOS_NOTARY_PROFILE` (имя профиля Keychain). Скрипт включает Hardened Runtime с разрешением JIT, отправляет пакет в Apple, прикрепляет билет нотарификации, проверяет `stapler` и Gatekeeper и только затем упаковывает финальный ZIP. Без сертификата выпускается явно обозначенная ad-hoc сборка. Пароли и сертификаты в репозитории не хранятся.

Иконка приложения: `src/CafeMenuConverter.App/Assets/app-icon.svg` — векторный исходник с фисташковым фоном; `app-icon.png` — экспорт 4096×4096 без потерь. В окне используется векторный `DrawingImage` из `Assets/AppIcon.axaml`, поэтому изображение остаётся чётким при любом масштабе интерфейса. Для macOS каждый размер ICNS (до 1024×1024, включая Retina), а для Windows каждый размер ICO (16–256 px) рендерится напрямую из SVG. Готовые ресурсы хранятся в проекте и включаются в сборки автоматически. После обновления SVG выполните на macOS `npm ci --prefix build` и `bash build/create-icons.sh` (нужен Node.js), затем обычную публикацию. Node.js и sharp нужны только для обновления графики, не для сборки или запуска приложения.

В интерфейс встроены T-Sans для заголовков и Neue Haas Unica W1G для текста, поэтому установка шрифтов в ОС не требуется. Источники фирменного знака и шрифтов, авторские права и условия из метаданных приведены в `build/licenses/brand-assets.txt` и включаются в архивы приложения.

Обычная команда `dotnet` использует стандартный кеш NuGet. `publish.sh` по умолчанию использует кеш в `artifacts`, чтобы работать и в ограниченной среде. Для остальных команд в такой среде:

```sh
export NUGET_PACKAGES="$PWD/artifacts/nuget"
export NUGET_HTTP_CACHE_PATH="$PWD/artifacts/nuget-http"
dotnet test CafeMenuConverter.sln
```

## Проверки

Тесты покрывают исходные парсеры, оба полных PDF, все 300 строк, переносы между колонками/страницами, четыре страницы на день, неизвестные разделы/время, повреждённые и зашифрованные файлы, отмену, сохранность существующего файла, OpenXML и состояние GUI.

Эталоны `expected-*.json` получены независимым извлечением через pdfplumber, а не копированием результата производственного парсера. Все поля совпали с результатом PdfPig; визуально проверены макеты и граничные случаи на отрендеренных страницах. Сентябрьский XLSX используется только для проверки схемы, поскольку содержит другое меню.

Контрольные количества: завтрак **145** (30/28/30/28/29 по дням), обед **155** (31 каждый день). Завтрак даёт два предупреждения о полностью нулевых КБЖУ, обед — ни одного.

Инструмент диагностики разработчика:

```sh
dotnet run --project tools/CafeMenuConverter.Inspect -- references/menu-for-humans.pdf
dotnet run --project tools/CafeMenuConverter.Inspect -- references/menu-for-humans.pdf --words
```

`build/verify-release.py` проверяет **готовый релиз**: переносит единственный EXE / распакованную `.app` в другую папку с пробелами и кириллицей, исключает установленный .NET из окружения, открывает настоящее окно, рендерит интерфейс, конвертирует оба PDF и независимо сравнивает все 14 полей всех 300 строк XLSX с эталонами. С `--block-network` сетевой доступ процесса блокируется средствами ОС. На Windows этот флаг требует административных прав только у проверочного скрипта, создающего временное правило Firewall; само приложение их не требует.

```sh
python3 build/verify-release.py artifacts/releases/CafeMenuConverter-osx-arm64.zip artifacts/verification/osx-arm64 --block-network
```

В GitHub Actions (`.github/workflows/releases.yml`) эти проверки выполняются отдельно на Windows x64, macOS Apple Silicon и Intel. На одноразовом Windows runner перед запуском дополнительно убираются доступные установки .NET. Отчёты содержат SHA-256 проверенного файла, загруженные модули, XLSX и снимок окна. Кросс-компиляция сама по себе не считается проверкой запуска.

Технический режим приложения для автоматизации: `--verify-release <каталог PDF-фикстур> <новый каталог отчёта>`. При обычном запуске он не активен. Подробности исходного ревью: [docs/REVIEW.md](docs/REVIEW.md).
